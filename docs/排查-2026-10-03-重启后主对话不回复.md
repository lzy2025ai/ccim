## 已排除的怀疑

1. **「主对话没写完的代码导致卡住」——不成立。** `7449314` 相对 `b44d8ac` 在 `session.py` 里多出的东西：
   `Turn.on_end`、`Turn.follow_through` 两个字段（默认空 / False）、`Chat.send_now()`（只有点「立即发送」才会调用）、
   `_turn` 结束时执行 `on_end`（空列表）、`_turn_inner` 里 `if t.follow_through and t.unseen`（follow_through 恒为 False）。
   用户没点过「立即发送」，这些对普通一轮没有影响。**所以回退 `eca851b` 其实不是修复**（但无害，改动已存到分支 `wip/send-now`）。
2. **「接上被打断的对话会卡住」——两种复现都没卡住。** 复现脚本：`/tmp/repro/run.py`（临时目录、假渠道、haiku）。
   - 先正常聊一轮 → 再让它跑 `sleep 25`，跑到一半像安全重启那样 `bridge.shutdown()` → 新进程接上再问：正常回复，记得前文。
   - 同上，但第二步改成 `SIGKILL` 直接杀进程：同样正常。

## 强线索（待验证）

主对话和话题、和复现的唯一明显区别：**重启时有一个后台任务被杀，接上会话后 Claude Code 先补了一轮「后台任务通知」**
（`<task-notification>` → "No response requested."），然后才处理用户的问题。

推测：这多出来的一轮，让 ccim 在 `_turn_inner` 里对「这一轮什么时候结束」的判断错位了。可能的样子（都没验证）：
- 第一轮（通知那一轮）的 `ResultMessage` 被当成用户这一轮的结束，而那一轮回答是 "No response requested." 或空……
  但如果是这样，应该会发出一条奇怪的回复并记 `→ 回复`，日志里没有；
- 或者 `receive_messages()` 的读取在两轮交界处卡住，等不到用户这一轮的 `ResultMessage`；
- 或者跟 0.6.0 的 INJECT_GRACE / `t.unseen` 逻辑有关（19:28 那条消息是在主对话忙时到的，是否走了「补充给它」？日志里没有对应记录，需要确认）。

尝试复现这条线索时（让 Claude 用 `run_in_background` 启动 `sleep 8` 后马上停掉），后台命令被 auto 模式拦下没启动，
只出现了 "No response requested." 那一轮、没有 task-notification，ccim 正常结束——**线索没被复现，也没被排除**。

## 顺带发现的另一个问题（已确认）

对话的**第一轮**就被打断时，ccim 还没拿到 `ResultMessage`，不会保存 session_id；重启后变成一个全新的对话，前面说的都丢了。
（复现：上面脚本不先聊一轮、直接跑 sleep 再打断，接上后 Claude 说「这是对话开始」。）
修法：连上时从 SDK 的初始化消息里拿 session_id 就保存，不等 ResultMessage。
