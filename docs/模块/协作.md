# 协作：群聊、@ 其他 Agent、搜对话、转交

改 groups.py、mentions.py、projects.py、search.py，或 send_to_chat / ask_agent 前先读。

- `ccim/groups.py`：群聊（#15，取代项目入口；项目页还在，只是导航里没有了）。群聊 = Agent 的网页对话 meta 里有 members（除主 Agent）、
  note（群聊说明，note_at）。不 @ 时主 Agent 回答；@ 走 mentions（@ 到不在群里的顺手拉进来，别的电脑上的走 /api/peer/task kind=mention），
  各人看到哪记在主对话 meta 的 ctx_upto。群聊说明改过后各人下一次被问到时在消息前面带上（note_seen）。
  启动时 `migrate_projects` 把每个项目复制成群聊（只做一次，state 的 groups_from_projects）：第一个本机成员当主 Agent 并 fork 它在项目里的会话，
  记录转成 user / answer / mention，指向项目的定时任务改成 kind=group
- `ccim/mentions.py`：网页对话里 @ 其他 Agent（#11）。每个被 @ 的 Agent 一个子对话 m-<对话>-<Agent>（meta 里 mention_of，不进列表），
  再被 @ 时接着它的会话，只补上它上次（ctx_upto）之后对话里的新内容；结果记在主对话里（type=mention，按 id 合并）。
  之后不带 @ 发消息时，主对话的助手没看过的回答（done_at > mention_seen）拼在消息前面交给它。删主对话连子对话一起删
  用户 @ 的成员正在做这个对话交给它的活（子对话 `current` 就是那条 mention 的 Task）：`_inject` 补充进它这一轮（#304），和直接跟主 Agent 说话一样，
  那条 mention 记上 joined（补充那几条消息的 id），网页把回答挂在最后一句补充下面。补充本身也是个 Task：来晚了、Claude 没接着处理时
  session 会把它单独排一轮，`_unjoin` 在那一轮做完时看它是不是在队列里 / 正在做 / 已结束，是就给它补一条自己的 mention。
  ask_agent、侧边对话、别的电脑上的成员、/queue 开头的照旧排队
  对话里的助手自己找人（#179）：`platform_agents`（`_visible_agents`：本机的 + 别的电脑缓存里的，访客只有自己建的和共享给它的）、
  `ask_agent`（session.py `_ask_agent`，平台上的对话都有，Skill 助手除外；Codex 经 toolsock 一样有）。找别人 = `Mentions.send` 在当前对话里替它 @
  （被 @ 的成员找人就在外层群聊里 @），记录带 by（Agent 编号，没选 Agent 的对话是 ASSISTANT），网页 threadOrder 把它和回答排在这一轮回答前面；
  找自己 = `Platform.dispatch_self` 新开同样设置的对话（meta 的 dispatched_from，同一个 Agent 时挂在发起的对话下面）。
  wait 时等回答（最多 20 分钟）作为工具结果交回，所以 unseen 不再重复带；不等或没等到的，做完 `Platform.deliver` 作为新一轮交回发起的对话。
  被 @ 的成员（子对话）一定等。防失控：Task.depth（派出去的 +1，经 /api/peer/task 带到别的电脑），到 MAX_DEPTH 不能再派；一轮最多 MAX_ASKS 次
  列表、任务面板里群聊按「谁在干活」显示（#192）：`Mentions.where` 记 mention → (群聊, 成员, 子对话)，`crew` 给 chat_view；成员在干活时不算等你处理，最后回答的是成员时 last_by 是它（面板头像），一句话进度也按它的回答写；网页 `working(c)` = 主 Agent 或成员在干活（c.busy 只管主 Agent，输入框用）。对话列表里 @ 过成员的对话，不在干活时标题处换成 last_by 的头像和名字（#302）；干活时第二行已有名字，最后是主 Agent 回答的，都还是标题
  网页输入框的 @ 列表选一个就关（#323）。不是和 Agent 的对话、第一句就 @ 了人的，之后输入框一直带着第一句的 to（`stickyAt`，从对话记录推，不另存）；
  点掉其中一个就不再带，记在浏览器 localStorage 的 ccim.atOff（#327）
  成员 Agent 的列表统一成子对话（#409，取代 #359 的列群聊本身）：`platform._agent_chats` 列它所有的对话，子对话标题用群名、带 member
  （网页标「成员」，侧边对话里被 @ 的标「侧边对话」，chat_view 的 group 给群名、群在哪台电脑）；群主 Agent 的群就是它自己的对话。
  子对话里群里 @ 它的那条记着 from_chat（群主 Agent 找它的还有 from_by），网页写「在群聊「x」里 @ 的」，点了进群。
  它从群里派出去的对话（dispatched_from=群）在前端挂到它的子对话下面（不写 parent：子对话跟着群删）。群聊标为已完成，本机子对话跟着标。
  头像卡片 `agent_recent(at=当前对话)`：它在当前群里的子对话排第一（here），只是成员的群不再列群本身。
  群里被 @ 的成员也有 start_work（`session._can_work`：本机、外层在本机、不是别的电脑派来的）：`Platform.work` 新开它自己的对话（dispatched_from=群），
  群里记 type=work 卡片，做完 `Mentions.report` 交回它在群里的子对话、在群里汇报，文件附在汇报下面。网页对话页的 recHtml 画 work 卡片和
  report 的 mention（它前面没有用户消息，mentionGroup 挂不上）；threadOrder 里 work 和 mention 一样按顺序排，不然会被挪到前面那条 @ 消息之前。
  新对话在它的列表里按 dispatched_from 挂在群下面（只在前端改 parent，不写进 meta：parent 还管分叉、删除）；会话页列表本来就不列 Agent 的对话。
  坑：以前侧边对话那边判断 remote_project 默认取了 True，本机的被 @ 子对话其实拿不到 start_work，这次一起改了
  侧边对话里也能 @（#290）：外层是侧边对话，被 @ 的只读，细节见平台.md 的侧边对话
  一句同时 @ 几个人（#331）：每个人的提示里带上还 @ 了谁，话里分了工的只做自己那份，没分工的各自完整回答（不在发出前选「对比 / 分工」，
  页面也不猜）。回答默认上下排，宽屏上每组可切并排（localStorage 的 ccim.sideBySide 记消息编号），挂件、手机上一直上下排
  子对话里能直接聊（#409，取代 #150 的一开口就另开）：消息只在子对话里，不进群聊记录和群里别人的上下文；交给它时前面说明
  「这是子会话里直接说的，群里看不到」，它自己判断要不要同步到群里。干活中来的照旧补充进这一轮。答完提示只看子对话最后一条用户消息：
  群里 @ 的（from_chat）只在群聊提示，直接说的在子对话提示（`_direct_turn`）。
  任务面板（#417）：直接聊的那一轮不经过群聊，群聊那一行没有「在干活」，子对话又不算顶层，以前面板和角标都看不到。现在 summary 记 direct
  （最后一条用户消息不是 from_chat），`chat_head` 把直接聊、在干活 / 卡住 / 等批准 / 答完没看的子对话（`_direct_subs`）也带在整体状态里，
  chat_view 带 direct；网页 `onBoard`（顶层的 + mention_of 且 direct）算「正在干活」「等你处理」和角标，卡片标「成员」。
  子对话不进「对话」列表（有 agent），看过就离开整体状态，所以不会一直留在「等你处理」。@ 别人、拉人还是 `split_sub` 另开它的独立对话。
  发的文件、聊天记录、应用（`WebChannel._post`）：记在子对话；这一轮是群里 @ 它的（Task.group，mentions._run / _inject / peer_task 设）
  群聊也记一份带 sub。别的电脑上的成员：`peer_result` 的 sent 把这一轮发的文件、聊天记录带回，群里记 mid + sub，网页 sentUrl 去那台取。
  旧数据：以前另开出来的独立对话（split_from）原样留着。搜对话（search.sources）把本机子对话也算进来。
- `ccim/people.py`：群聊里的真人（#419）。对话 meta 的 people = [{id, by, at, state}]（id 是账号编号，主人是 peers.OWNER；state in / invited），
  建群的人（meta 的 account，没有就是主人）不在里面但总算在群里；子对话、侧边对话跟着主对话（`root`）。主人拉的直接进，别人拉的要对方同意
  （以后自己注册的账号改成看「是不是拉人的人建的」）。能拉的人 = 主人 + 来过这台电脑的访客（state 的 guests）。
  看得到：`share.chat_filter` 加上 `visible_map`（主对话 → 被拉进来的人，和 owner_map 一样缓存几秒，推送每条都要查，不能每次读 state.json）；
  和 Agent 的对话本来不进「对话」列表，被拉进别人群的（`Platform._joined`）照样列，网页也不跳到 Agent 页（那个 Agent 不在自己的列表里，
  `people_view.agents` 给群里 Agent 的样子，`agentOf` 找不到时用它）。推送带 `_p`，总控 `visible` 推给里面的人。
  能做什么：`share.check_people` 对所有人（主人被拉进访客的群也算）只放行 `MEMBER_GET / MEMBER_POST`，邀请没同意的只有 `INVITED`，
  /api/chat 只给空记录和邀请。@ 群里 Agent：访客能 @ 群里已有的（不必共享给它）。
  多人（≥2 个真人）时只回 @（`quiet`）：没 @ 主 Agent 的话记成 quiet、不交给它，下次 @ 它时 `backlog` 带上；@ 主 Agent 是 send 的 call，
  和别的 Agent 一起 @ 时 mentions 记那条、再用 logged 交给主 Agent。交给 Agent 的消息前面带 `note`（群里有谁）和【名字】；记录上 person。
  权限按这一轮是谁叫的（不是整个群降到最低）：`people.fence_for` 给 Platform.send 的 Incoming.speaker / mentions 的 prompt，
  Bridge 包成 `session.Speaker`（Task 带 fence）。fence：主人 ""（不圈）、建群的访客 None（对话本来的）、别的访客 `FENCE…` 占位账号
  （share.fence 认不出它的文件夹，只留工作目录、平台 Skill）。Claude Code 的沙箱和权限规则是启动时定的，一轮里改不了，
  所以 worker 每轮开始前比一下，换了人就断开、按新的权限 resume 原会话（多等几秒）；`Chat.inject` 不把权限不一样的话补进正在跑的那一轮，
  排到后面单独一轮。访客叫的那一轮（`Chat.fenced`）工具只留发文件：不给搜对话、派活（ask_agent、start_work）、转交、日记、应用、管理员权限，
  权限模式固定 auto。访客 @ 别的电脑上的 Agent 直接拒（权限带不过去）。
  Agent 记得之前几轮看到的东西，访客那一轮问得出来：只管这一轮能动什么，管不了上下文。
  等你处理：各人看到哪记在 seen_of（建群的人还是 seen_at），被 @ 的记在 pinged；`share.mark_people` 在列表里按请求的人改 attention / at_me / invite。
  主人的名字取系统用户的全名（访客那边显示这个），取不到写「主人」。
- `ccim/projects.py`：项目（群聊，#8）。项目存平台 state.json 的 projects（只在主循环里改）；消息流记录 web/project-<编号>.jsonl
  （task、reply，reply 同一个 id 会被更新，`Logs.read` 按 MERGED 合并）。每个 Agent 在每个项目里一个网页对话 p-<项目>-<Agent>
  （meta 里 project / cwd，平台对话列表里不显示），派活 = 往这个对话里放 `session.Task`，同一 Agent 自然排队、Agent 之间看不到彼此。
  对比且项目目录是 git 仓库：每人 `git worktree`（~/.ccim/worktrees/，分支 ccim/<任务>-<Agent>）+ 新对话 p-…-<任务>，
  做完自动提交到分支；「用这个」= squash 合并进项目目录当前分支记成一次提交，项目目录有没提交的改动时拒绝，冲突就 reset 回去。
  回答还没出来时状态是 queued，网页按「这个对话正在干活、而且是它最早没做完的一件」显示成干活中；平台重启后没做完的显示 lost
- `ccim/search.py`：Agent 搜自己参与过的对话（#180）。`search_chats` / `open_chat`（session.py `_search_tools`，平台上 Agent 的对话都有，含群聊里被 @ 的子对话）。
  范围 `sources`：网页里它的对话、它是成员的群聊、@ 过它的外层对话（本机子对话的内容都在外层里，不重复），别的电脑上群聊的子对话，
  飞书、微信（external_chats），工作目录下最近 100 个终端会话；访客只有自己账号的网页对话。
  没选 Agent 的对话（助理，#294）也有这两个工具，aid 是 None，范围是所有助理对话（含右下角挂件里的），不含 Agent 的、侧边对话、Skill 助手，也没有飞书、微信、终端；
  它们因此不再有 list_chats / read_chat。关键词都要出现在同一条消息里，不建索引；
  别处的记录自己缓存（不挤 history 的 50 个）。不写关键词 = `listing`：列出它参与的所有对话（在哪些群、主 Agent 还是成员、群里有谁）。
  平台上 Agent 的对话（`_searchable`）不再给 list_chats / read_chat（两套重叠，实测会挑错），系统提示换成 LOOK_AROUND_PF；send_to_chat 也认这里的编号。结果里它自己说的写「你」：Agent 不一定记得自己叫什么，写名字会被当成别人。
  角色说明（`role_note`）也带上「你是这个平台上的 Agent「名字」」
  引用（#199）：Agent 页的输入框打 #（`refTyped`，候选是 agentSide.chats）或列表三点菜单「引用到输入框」，chatRefs 随 /api/chat/send 的 refs 发出；
  `Platform._refs` 只认同一个 Agent、同一个账号的，记在用户那条的 refs 里，交给助手时前面拼一句带 open_chat 编号的说明。@ 别人时不能带（那是别的 Agent 的对话）。
  网页对话的标题在 `Platform.send` 里用用户原话定（session `_turn` 拿到的是拼了前缀的）
- 对话之间转交（#121）：平台上的对话（私聊、群聊里被 @ 的成员、定时任务）都有 `send_to_chat`（`_send_to_chat` → `Platform.relay`），
  只限同一个 Agent 的对话（跨 Agent 走群聊 @）；被 @ 的成员转交时来源记成那个群聊。目标按 list_chats 的会话编号找：
  已经有网页对话用着这个会话就交给它，终端、桌面端的 Claude 对话就像网页里接着聊一样新开一个网页对话（link）；飞书、微信的不转。
