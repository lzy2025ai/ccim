# 稳定版、升级、新电脑接入

改 runtime.py、upgrade.py、onboard.py、join.sh 前先读。重启、试用、开发页的细节见 开发页与重启.md。

- `ccim/runtime.py`：稳定版 / 开发版、安全重启、`ccim promote`。稳定版在 `~/.ccim/stable/<版本>/`（独立 venv，从某次提交装），
  `channel.json` 记 current / previous；项目的 `runtime`（dev / stable）、`stable_version`（钉版本）在登记表里。
  启动命令带 `-P`，否则在 ccim 代码目录里跑稳定版会导入目录里的开发代码。安全重启由独立进程做（优先用稳定版跑），
  新版本 60 秒内没连上或很快退出就用稳定版顶上（state 里 fallback=True），结果主动私聊主人。
  venv 的 python 是指向系统 python 的软链，判断属于哪个环境要看目录（`_env`），不能 realpath python 本身
- `ccim/daemon.py` 常驻（#522）：macOS 用 launchd（LaunchAgent），Linux 用**用户级 systemd**（~/.config/systemd/user/ccim-<key>.service，
  Restart=on-failure、RestartSec=30，等同 launchd 的 KeepAlive SuccessfulExit=false），都没有（容器、没开 systemd 的 WSL）就退回后台跑，开机不会自启。
  选用户级不选系统级：ccim 以普通用户跑，自己要随时停、起、重启（升级、试用、安全重启），系统级每次都要 root。代价是用户级服务默认要有人登录才跑，
  要 `loginctl enable-linger <用户>`：join.sh 以 root 运行时替它开；普通用户 `ccim join` 时试着自己开，开不成就提示用管理员开。
  su / sudo -u 进来时没有 XDG_RUNTIME_DIR，`_user_env` 补成 /run/user/<uid>，否则 systemctl --user 连不上。
  坑：systemd 托管的进程，子进程默认在同一个控制组里，停这个服务会连子进程一起停。安全重启、升级、promote 这些「另起一个独立进程」的，
  一律经 `daemon.detach` 包一层 `systemd-run --user --scope`（只在 systemd 托管的进程里，看 INVOCATION_ID），不然独立进程刚停掉平台就被一起杀了。
  单元里的参数用双引号括起来，% 写成 %%，ExecStart 里 $ 写成 $$。
- Linux 以 root 运行 join.sh（#522）：ccim 和 Agent 不用 root 跑。用 sudo 运行的用 SUDO_USER，直接 root 登录的建 ccim 用户
  （CCIM_USER 指定、CCIM_AS_ROOT=1 坚持 root），开 linger，然后 `su - 用户` 从总控重新取 join.sh 再跑一遍（curl | sh 时拿不到脚本本身）。
  免密 sudo：给 ccim 建的用户（或默认的 ccim 用户）写 /etc/sudoers.d/ccim（先写临时文件、`visudo -cf` 校验过才换上），没装 sudo 先用系统的包管理器装；
  `--no-sudo`（或 CCIM_NO_SUDO=1）不给，已有的 /etc/sudoers.d/ccim 删掉。沿用原用户（sudo 运行、CCIM_USER）的不改它的权限，
  以普通用户跑到最后时 `sudo -n true` 不通就提示怎么开。Agent 用管理员权限的流程见 平台.md 的 admin.py。
- `ccim/upgrade.py`：版本和网页上升级（#37）。`info` 认出是开发版（代码目录，git 提交）、稳定版（~/.ccim/stable 目录名）、
  发布版（uv tool 装的，direct_url.json 里的提交）还是服务器（~/ccim-hub/deployed.txt）；发布版和 GitHub 上最新提交比（后台问，一小时一次）。
  state 里的 ccim → machine_info 带到网页。升级由独立进程（`python -m ccim.upgrade run`）做：uv tool upgrade → 用新装的 python 问新提交 →
  逐个 safe_restart 在跑的项目（平台最后）→ 平台没起来就 `uv tool install --force git+…@旧提交` 再重启。uv 会换掉整个环境，
  所以这个进程开头就把 daemon、registry、runtime 都导入好。结果在 ~/.ccim/upgrade.json
- `ccim/onboard.py` + `ccim/join.sh`：新电脑一条命令接入（#175）。总控（服务器 /join.sh、局域网 Mac 的 8978 端口 /join.sh）给出填好地址、
  版本、安装包校验值的 join.sh；安装包 /peer/dl/<文件名> 是总控把自己正在跑的 ccim 现打的 wheel（自己写 zip，版本号 0.19.0+g<提交>，
  缓存在 ~/.ccim/dist），不经过 GitHub。脚本先看本机 ccim（没装 / 不同版本 / 一样 / 开发版不动）和 hub.json（已加入这个 / 别的总控：有终端就问，没有就停），
  连不上 PyPI、GitHub 时 uv、依赖、Python 走国内镜像（阿里云等 PyPI 镜像、npmmirror 的 python-build-standalone），`uv tool install --no-build`
  （新版 cryptography 不出 Intel Mac 的包，不让它在本机编译）。整个脚本包在 main 里（curl | sh 时子命令会读走后面的脚本）；sh 里中文紧跟变量名要写 ${VAR}。
  进度：脚本和 `ccim join` POST /peer/progress（配对码对得上才推 type=pairing，只带 pid，服务器上只推给生成配对码的账号），配对码用过后留到过期。
  `ccim join` 已加入同一个总控时先用签名请求问还认不认（`peers.check_joined`），认就不配对、只确认在运行；--restart 是脚本升级后重启在跑的进程。
  `upgrade.info` 从版本号认出从总控装的（url=hub），网页升级从总控下载（`_from_hub`），装回原来版本用 ~/.ccim/dist 里的旧包。
  测试：临时 HOME 起 `ccim hub --url http://127.0.0.1:18978 --port 18977 --peer-port 18978`，另一个临时 HOME、PATH 只留系统目录跑脚本（plist 里带 HOME，常驻进程用的也是临时目录）
